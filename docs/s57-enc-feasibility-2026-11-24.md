# S-57 ENC vector charts in SDL2 Plotter: feasibility research

Date: 2026-11-24. Research against primary sources (IHO publications, NOAA Office of Coast Survey, GDAL documentation, crates.io API, GitHub repositories and their source, Raspberry Pi product briefs). Every number below carries a source link; anything the sources did not state directly is marked **(estimate)** or **(unverified)**. The codebase-specific analysis is left for the main session in the last section.

## Summary verdict

Three routes were examined.

- **Route A: parse S-57 and render vectors on the device at runtime.** Feasible on a Pi 5 but the largest body of work. There is no Rust crate above the ISO 8211 record layer, so the S-57 feature model (spatial records, chain-node topology, update replay) and the S-52 symbology (around 3,000 look-up entries, 28 conditional procedures, 1,100 symbols) would be written and tested from scratch. The only S-52 asset set an open-source project ships is OpenCPN's GPL-2.0 data; the IHO's own Presentation Library is under cost-recovery copyright. OpenCPN, with a GPU and fifteen years of work, still precompiles cells because parsing at display time was too slow.
- **Route B: pre-process S-57 offline into Mapbox Vector Tiles in MBTiles, render vectors on the device.** Reuses a mature toolchain (GDAL's S57 driver, tippecanoe or GDAL's MVT writer, four maintained Rust MVT crates) and moves the parsing and topology problems off the boat. What remains is a styling problem (re-expressing the S-52 rules as a style over tile attributes, as the openwatersio project does for MapLibre) and a CPU rasterisation problem. `tiny-skia` with NEON is a credible rasteriser on an A76, at an estimated 20 to 40 ms per full redraw at 1280x800, so it belongs on a worker thread, not in the 16 ms loop. No GPU API is available under KMS/DRM except OpenGL ES 3.1, because the Pi's Vulkan driver lacks direct-to-display presentation.
- **Route C: pre-render S-57 offline into raster MBTiles, zero runtime change.** The only route that costs nothing in the main loop, and the way NOAA itself now serves ENC data to leisure users (Custom Chart PDFs with a user-chosen safety contour). It freezes the safety contour, the depth unit and the display category at render time and loses the pick report, so the safety-contour choice becomes a chart-building decision that must be labelled on the chart.
- **Chart availability dominates all three for this user.** There is **no free S-57 coverage of Portugal, Madeira or the Azores**: the Portuguese Hydrographic Institute sells its ENCs through IC-ENC under S-63 encryption, which a homebrew plotter cannot decrypt without an IHO-issued manufacturer key. Free S-57 cells exist for US waters (NOAA, 7,266 cells, weekly updates) and for European inland waterways (IENC), so any route is testable, but the charts the user actually sails on would stay raster, or o-charts inside OpenCPN. The S-57 format itself is frozen and will be joined by S-101 cells from 2026 with a dual-fuel period NOAA estimates at about a decade, so an S-57 reader built now is not wasted but will not be the last format.

## 1. The S-57 format

- **Encapsulation.** S-57 is the "IHO Transfer Standard for Digital Hydrographic Data", edition 3.1, November 2000; Part 3 of the standard is the data structure and clause 3 of Part 1 is titled "ISO/IEC 8211 encapsulation" ([S-57 Ed 3.1 main document](https://iho.int/uploads/user/pubs/standards/s-57/31Main.pdf)). ISO/IEC 8211 is a self-describing binary record format: a Data Descriptive Record (schema) followed by Data Records; each record has a leader, a directory of field tags and the field data ([iso8211 crate docs](https://docs.rs/iso8211/latest/iso8211/)).
- **Frozen edition.** The main document states "Edition 3.1 will remain frozen until at least November 2002" and that "all components of the Standard will remain unchanged for the duration of the freeze" ([31Main.pdf](https://iho.int/uploads/user/pubs/standards/s-57/31Main.pdf)). The IHO Encoding Bulletins page says "the IHO has frozen the contents of Edition 3.1 and no further changes will be made to it" ([IHO S-57 Encoding Bulletins](https://www.iho-ohi.net/mtg_docs/enc/enc_prod/s-57encodingbulletins.html)). Changes since then came as Supplement No. 1 (Ed 3.1.1, January 2007: three new object classes, three new attributes) and Supplement No. 3 (Ed 3.1.3, June 2014) ([Supplement 1](https://www.iho-ohi.net/files/publicat/free/files/s-57_sup1_ed_311_jan_2007.pdf), [Supplement 3](https://iho.int/uploads/user/pubs/standards/s-57/S-57_e3.1_Supp3_Jun14_EN.pdf)).
- **Records.** A cell holds feature records (type meta, cartographic, geo or collection; the object class in OBJL, attributes in ATTF/NATF, pointers to spatial records in FSPT) and spatial (vector) records (isolated nodes, connected nodes, edges with SG2D/SG3D coordinate fields, in a chain-node topology) ([31Main.pdf](https://iho.int/uploads/user/pubs/standards/s-57/31Main.pdf) Part 3). GDAL's driver "automatically collected and formed [geometry objects] into geometries on the features" and reports "a typical S-57 transfer will have in excess of 100 layers" ([GDAL S57 driver](https://gdal.org/en/stable/drivers/vector/s57.html)).
- **Object catalogue.** Appendix A chapter 1 lists the object classes and chapter 2 the attributes; SCAMIN is attribute code 133 and sits in attribute set B of essentially every geo class ([Appendix A ch. 1](https://iho.int/uploads/user/pubs/standards/s-57/31ApAch1.pdf), [ch. 2](https://iho.int/uploads/user/pubs/standards/s-57/31ApAch2.pdf)). Supplement 1 added object classes with codes 161 and 162 and Supplement 3 added attribute code 190, so the catalogue tops out around 160 object classes and 190 attribute codes; the round figure "159 feature object classes and 187 attributes" comes from a third-party write-up, **(unverified against the IHO PDFs' full tables)** ([osm2cdr S-57 deep dive](https://osm2cdr.com/en/blog/format-s57-deep-dive/)).
- **Product specification (Appendix B.1, Ed 2.0).** Navigational purpose codes in table 2.1: 1 overview, 2 general, 3 coastal, 4 approach, 5 harbour, 6 berthing; the code appears in the DSID INTU subfield and in the file name. Clause 2.2: "the resulting data set file contains no more than 5 Megabytes of data" and "Cells must be rectangular (i.e. defined by 2 meridians and 2 parallels)". Clause 5.6 shows an exchange set as ENC_ROOT with CATALOG.031, a base cell NL600021.000, updates NL600021.001 and .002 and a README.TXT; table 5.1 gives the edition/update numbering: a new data set is .000 with EDTN 1 UPDN 0, updates are .001, .002 and so on, a new edition restarts at .000 with EDTN 2 ([S-57 Appendix B.1](https://iho.int/uploads/user/pubs/standards/s-57/20ApB1.pdf)).
- **Real cell sizes and feature counts.** Computed on 2026-11-24 from NOAA's ENC product catalogue (52 MB XML) and three downloaded cells; FRID counts are ISO 8211 field-tag occurrences in the base file and so approximate the number of feature records ([NOAA ENC catalogue XML](https://www.charts.noaa.gov/ENCs/ENCProdCat_19115.xml), [NOAA ENC download](https://www.charts.noaa.gov/ENCs/ENCs.shtml)):

- **S-101 status.** The IHO Roadmap for the S-100 Implementation Decade v5.0 (October 2025) states: "S-100 ECDIS can be used voluntary from 1 January 2026 and will be mandated in new installations from 1 January 2029", that "identical coverage has to be provided for S-57 ENCs and S-101 ENCs for a transition period", that "the start date of S-101 ENC provision service in 2026" is known to the ECDIS industry, and that "encoding remains ISO-IEC8211" for S-101 ([Roadmap v5.0](https://iho.int/uploads/user/About%20IHO/Council/S-100_ImplementationStrategy/S100_Roadmap_Decade_v5.0_clean_October2025.pdf)). NOAA's transition plan (November 2023) says concurrent S-57/S-101 production starts in 2026, that "In approximately 10 years, the S-101 product specification will fully replace S-57" and that the dual-fuel period "is estimated to be around a decade" ([NOAA S-57 to S-101 transition plan](https://iho.int/uploads/user/Inter-Regional%20Coordination/WEND-WG/WENDWG14/WENDWG14_2024_05.1Ac_EN_NOAA%20US%20Transition%20Plan%20S-101%2021%20November%202023.pdf)). Public S-101 cells today: the UKHO publishes S-101 trial datasets aligned with the GB S-57 scheme for testing ([ADMIRALTY S-100 trial data](https://www.admiralty.co.uk/access-data/s-100)); NOAA's download site still lists S-57 only as of 2026-11-23 ([NOAA ENC download](https://www.charts.noaa.gov/ENCs/ENCs.shtml)). Practical consequence: S-57 is what a plotter will meet for the rest of this decade, and an S-57 reader built now is not wasted, but S-101 changes the feature catalogue and the portrayal catalogue, so route A would face a second format within the Pi's service life.

## 2. Chart availability and licensing for a leisure user

- **NOAA (US waters).** "The Electronic Navigational Charts are available in S-57 format"; the full set was 770 MB zipped on 2026-11-23 with ten-day and one-week delta packages ([NOAA ENC download](https://www.charts.noaa.gov/ENCs/ENCs.shtml)). The user agreement: "NOAA updates the ENCs for Notice to Mariners on a weekly basis", "The NOAA ENCs are intended for navigational use", "You may download, use, and redistribute them without restriction, and without payment to NOAA" ([NOAA ENC user agreement](https://www.charts.noaa.gov/ENCs/ENC_Agreement.shtml)). NOAA is rescheming to "over 7,300 ENCs in twelve standard scales" ([NOAA Custom Charts](https://www.nauticalcharts.noaa.gov/charts/noaa-custom-charts.html)). NOAA cancelled all raster products in December 2024, including the RNC tile service ([Farewell to Traditional Nautical Charts](https://www.nauticalcharts.noaa.gov/charts/farewell-to-traditional-nautical-charts.html)), so for US waters ENC-derived output is the only official product. The NOAA Custom Chart (NCC) tool renders ENC data to geo-referenced PDFs with depths in metres, feet or fathoms and "the depiction of a safety contour based on a vessel's draft", refreshed from ENC data "updated every weekday" ([NOAA Custom Charts](https://www.nauticalcharts.noaa.gov/charts/noaa-custom-charts.html)). ENC Direct to GIS exists as an ArcGIS web application ([encdirect.noaa.gov](https://encdirect.noaa.gov/)); the "ENC Online" page returned HTTP 404 on 2026-11-24 **(unverified whether it still exists)**.
- **S-63 (Primar, IC-ENC, UKHO and almost every other HO).** S-63 Ed 1.2.1 defines: "M_KEY: ECDIS manufacturer's unique identification key provided by the Scheme Administrator to the OEM. It is used by OEMs to encrypt the HW_ID when creating a userpermit. HW_ID: The unique identifier assigned by an OEM to each implementation of their system" and "User Permit: Encrypted form of HW-ID uniquely identifying the ECDIS system" ([IHO S-63 Ed 1.2.1](https://iho.int/uploads/user/pubs/standards/s-63/S-63_2020_Ed1.2.1_EN_Draft_Clean.pdf)). The IHO requires a Data Server Agreement and an OEM Agreement for participation ([IHO Data Protection](https://iho.int/en/data-protection-s-100/s-57), [OEM Agreement v1.1.3](https://iho.int/uploads/user/pubs/standards/s-63/S-63_OEM_Agreement_v1.1.3.doc)). Without an M_KEY from the IHO Secretariat a homebrew plotter cannot produce a user permit and no data server will issue cell permits: S-63 is effectively closed to this project. Prices through Primar distributors are "by quotation"; one distributor shows indicative figures of roughly 16 to 25 EUR per cell for a three-month licence ([Nautic Way ENC page](https://www.nautic-way.com/en/primar-enc-s57-s63-digital-nautical-chart-for-ecdis/7690-15-vector-enc-s57-s63-maritime-bookshop-nautic-way.html), [PRIMAR products](https://www.primar.org/products)).
- **Portugal, Madeira, Azores.** The Instituto Hidrográfico states ENCs "are comercialized via International Centre for Electronic Navigational Charts (IC-ENC) and by authorized distributors"; only the inland IENCs of the Douro and Guadiana waterways are free, and the free IHPT ENC WMS covering mainland Portugal, Madeira and the Azores is a view-only S-52-styled web map service ([Instituto Hidrográfico, Nautical Charts](https://www.hidrografico.pt/op/41), [IHPT ENC WMS FAQ](https://faq.hidrografico.pt/books/hidrografico/page/servico-de-visualizacao-das-cartas-eletronicas-de-navegacao-ihpt-enc-wms/export/html)). Confirmed: no free S-57 for the user's cruising ground.
- **Inland ENC (IENC).** The German waterways administration publishes IENC zip files "in the official S-57 exchange format" per river, free, with an ATOM feed (Rhein 13.61 MB, Main-Donau-Kanal 7.43 MB, Donau 4.52 MB on the listing) ([ELWIS IENC](https://www.elwis.de/DE/dynamisch/IENC/)); Danube states publish theirs through national portals ([Danube Commission ENC page](https://www.danubecommission.org/dc/en/danube-navigation/electronic-navigational-charts-enc-for-the-danube-river/)). Useful as free European test data; useless at sea.
- **o-charts (OpenCPN).** oeSENC is "an encrypted format optimized for OpenCPN", installed through the o-charts plugin with a system fingerprint, assignable to "more than one device, usually five" or a USB dongle, minimum OpenCPN 5.6.2 ([o-charts manuals](https://o-charts.org/manuals/), [OpenCPN oeSENC manual](https://opencpn-manuals.github.io/main/oesenc/0.1/index.html), [o-charts_pi](https://github.com/bdbcat/o-charts_pi)). The plugin wrapper is GPL-2.0; the decryption server is not open. Not usable from this plotter.
- **S-52 Presentation Library terms.** The IHO text on the PresLib Ed 4.0.3 addendum and on S-52 Ed 6.1.1: "This work is copyright ... no part may be translated, reproduced by any process, adapted, communicated or commercially exploited without prior written permission from the International Hydrographic Organization" and may be "distributed for general information, on no more than a cost recovery basis" with an attribution statement ([S-52 PresLib 4.0.3 Addendum](https://iho.int/uploads/user/pubs/standards/s-52/S-52%20PresLib%20Ed%204.0.3%20Part%20I%20Addendum_Clean.pdf), [S-52 Ed 6.1.1](https://iho.int/uploads/user/pubs/standards/s-52/S-52%20Edition%206.1.1%20-%20June%202015.pdf)). That is not an open-source licence. What OpenCPN does: it ships `chartsymbols.xml` (2.19 MB), `rastersymbols-day/dusk/dark.png`, `S52RAZDS.RLE` (1.28 MB), `s57objectclasses.csv` and `s57attributes.csv` in `data/s57data` ([OpenCPN data/s57data listing](https://api.github.com/repos/OpenCPN/OpenCPN/contents/data/s57data)), and its `s52plib.cpp` and `s52cnsy.cpp` carry GPL-2.0-or-later headers crediting David Register and Sylvain Duclos ([s52plib.cpp](https://github.com/OpenCPN/OpenCPN/blob/master/libs/s52plib/src/s52plib.cpp), [s52cnsy.cpp](https://github.com/OpenCPN/OpenCPN/blob/master/libs/s52plib/src/s52cnsy.cpp)). The older libS52 project notes the official PresLib "is not available for free download" and that it used "an alternate non-conforming ECDIS library" ([sduclos/S52](https://github.com/sduclos/S52)). Whether OpenCPN's XML is an independent re-expression or a derivative of IHO data is not stated anywhere found **(unverified)**; reusing it would in any case bring GPL-2.0 obligations into this codebase, and the openwatersio project ships a `.dai` parser and "the S-52 Presentation Library in JSON format" under Apache-2.0, which has the same provenance question ([openwatersio/enc-tiles](https://github.com/openwatersio/enc-tiles)).

## 3. What an S-52 display needs

- **Structure.** S-52 Ed 6.1.1 describes the Presentation Library as Part I with "six appendices ... One (Appendix A) contains values for the three colour tables; the other five (Appendices B-F) contain symbolization look-up tables", Part II with mariners' navigational objects, and an addendum that is "a paper based description of the symbol library as graphics" ([S-52 Ed 6.1.1](https://iho.int/uploads/user/pubs/standards/s-52/S-52%20Edition%206.1.1%20-%20June%202015.pdf)). The PresLib 4.0.0 Part I lists the five look-up tables as paper-chart point symbols, simplified point symbols, line symbols, plain area boundaries and symbolized area boundaries, and says that where symbology depends on context, "for example a depth area, whose colour fills depends on the choice of the safety contour", the look-up table "refers the decision to a conditional symbology procedure" ([PresLib 4.0.0 Part I, legacy IHO site](https://legacy.iho.int/iho_pubs/draft_pubs/PresLib_e4.0.0/Part_I/S-52_PresLib_e4.0.0_Part%20I_Clean_Draft.pdf); the legacy host did not resolve on 2026-11-24, quotes come from search snippets, **(unverified directly)**). The 4.0.3 addendum (December 2020) is a 564-page symbol catalogue ([PresLib 4.0.3 Addendum](https://iho.int/uploads/user/pubs/standards/s-52/S-52%20PresLib%20Ed%204.0.3%20Part%20I%20Addendum_Clean.pdf)). S-52 6.1.1 sets the design rule that matters for safety: "important features (e.g. own-ship symbol, own-ship safety contour, etc.) [are] more conspicuous than minor features" and the safety contour "is a thick line and has a sharp change in the colour of the depth areas" on either side ([S-52 Ed 6.1.1](https://iho.int/uploads/user/pubs/standards/s-52/S-52%20Edition%206.1.1%20-%20June%202015.pdf)). The display categories Display Base, Standard and Other are IMO Performance Standard concepts referenced throughout the same document.
- **Size of the job, measured on OpenCPN's implementation** (counts made on 2026-11-24 over `chartsymbols.xml` and `s52cnsy.cpp` at master): 7 colour tables (DAY_BRIGHT, DAY_BLACKBACK, DAY_WHITEBACK, DUSK, NIGHT, DAY_HICON, NIGHT_HICON) with 441 colour entries; 3,057 look-up entries, of which 574 Displaybase, 1,754 Standard, 529 Other; 1,093 symbol definitions, 59 line styles, 30 fill patterns; 115 look-up instructions that call a conditional procedure; 28 conditional symbology procedures implemented: CLRLIN01, DATCVR01, DEPARE01, DEPCNT02, DEPVAL01, LEGLIN02, LIGHTS05, LIGHTS06, LITDSN01, OBSTRN04, OWNSHP02, PASTRK01, QUALIN01, QUAPNT01, QUAPOS01, SLCONS03, RESARE02, RESTRN01, SEABED01, SNDFRM02, SOUNDG02, SOUNDG03, TOPMAR01, UDWHAZ03, VESSEL01, VRMEBL01, WRECKS02, SYMINS01 ([chartsymbols.xml](https://github.com/OpenCPN/OpenCPN/blob/master/data/s57data/chartsymbols.xml), [s52cnsy.cpp](https://github.com/OpenCPN/OpenCPN/blob/master/libs/s52plib/src/s52cnsy.cpp)).
- **Minimal useful leisure subset (estimate).** A sailor needs the Display Base plus the Standard category items that keep the boat off the bottom: DEPARE fills keyed to a safety contour (DEPARE01 and DEPCNT02 logic), LNDARE and COALNE, SOUNDG with the shallow/deep colour split (SOUNDG02 and SNDFRM02 glyphs), OBSTRN and WRECKS and UWTROC with the isolated-danger logic (OBSTRN04, WRECKS02, UDWHAZ03), LIGHTS with sector arcs (LIGHTS05 or 06, LITDSN01 for the text), BOYxxx and BCNxxx with TOPMAR01, RESARE and RESTRN outlines, and a day plus a night colour table. **(estimate)**: roughly 8 to 10 of the 28 procedures and perhaps 300 to 500 of the 3,057 look-up entries cover that, but each procedure is a page of branching logic and the symbol glyphs still have to come from somewhere licensed. Full compliance (every procedure, every pattern fill, text placement rules, SCAMIN handling, overscale indication, pick reports) is what OpenCPN has spent since 2010 on.

## 4. Libraries

### 4.1 GDAL/OGR S57 driver and the `gdal` crate

- Read-only driver, built in by default. Needs `s57objectclasses.csv` and `s57attributes.csv` at runtime (`S57_CSV` or the working directory). "The S-57 reader will normally read and apply all updates files to the in memory version of the base file on the fly." Open options: `UPDATES=APPLY|IGNORE` (default APPLY), `SPLIT_MULTIPOINT` (default OFF; split multipoint soundings), `ADD_SOUNDG_DEPTH` (adds a DEPTH attribute, needs SPLIT_MULTIPOINT), `RETURN_PRIMITIVES` (expose IsolatedNode, ConnectedNode, Edge, Face layers), `LNAM_REFS` (feature-to-feature links from FFPT), `RETURN_LINKAGES`, `PRESERVE_EMPTY_NUMBERS`, `RECODE_BY_DSSI`, `LIST_AS_STRING`. Export is "preliminary ... not properly documented" ([GDAL S57 driver](https://gdal.org/en/stable/drivers/vector/s57.html)).
- Rust binding: `gdal` 0.19.0 and `gdal-sys` 0.12.0, both MIT, released 2025-12-23, 4.4 M downloads ([crates.io gdal](https://crates.io/crates/gdal)). The README: "assumes a compatible version of GDAL is installed with the corresponding header files and shared libraries. This repository includes pre-generated bindings for GDAL 3.8 through 3.13 ... If you're compiling against another version of GDAL, you can enable the `bindgen` feature" ([georust/gdal README](https://github.com/georust/gdal/blob/master/README.md)). Debian bookworm, the base of current Raspberry Pi OS, ships `libgdal32` 3.6.2 ([Debian libgdal32](https://packages.debian.org/bookworm/libgdal32)), which is below 3.8, so on a stock Pi image the crate needs `bindgen` (and therefore libclang at build time) or a newer GDAL from backports or source. libgdal pulls a long dependency chain (PROJ, GEOS, SQLite, libtiff, curl, xml2, and the raster codecs); its installed size and dlopen cost on the Pi were not measured here **(estimate: tens of MB on disk, well under a second to load; must be measured)**. It also makes the binary non-static, against the project's single-binary habit, and its Windows dev build needs vcpkg or OSGeo4W GDAL.

### 4.2 Pure Rust

- `iso8211` 0.1.5 (MIT OR Apache-2.0, published 2026-05-01, 5,305 total downloads, 93 in the last 90 days, repo `pelorus-marine/ecdis`, 2 stars, last push 2026-05-18, about 1.5 K SLoC). It parses the DDR and data records and format control strings; its docs state "Interpreting feature codes, geometry, and portrayal is not done here" ([crates.io iso8211](https://crates.io/crates/iso8211), [docs.rs iso8211](https://docs.rs/iso8211/latest/iso8211/), [pelorus-marine/ecdis](https://github.com/pelorus-marine/ecdis)). `s-101` 0.0.1 from the same repo is "initial slice" S-101 decoding ([crates.io s-101](https://crates.io/crates/s-101)). No crate on crates.io implements the S-57 feature and spatial record model, chain-node topology assembly, or update application. That layer would be new code; for scale, the TypeScript project below covers it in a few thousand lines.
- `manimaul/njord` is a Rust "Open Source Electronic Navigation Chart Server" (Apache-2.0, 51 stars, pushed 2026-11-24) ([manimaul/njord](https://github.com/manimaul/njord)); whether it parses S-57 natively or shells out to GDAL was not inspected **(unverified)**.

### 4.3 Reference implementations in other languages

- **OpenCPN (C++, GPL-2.0, 1,518 stars, active).** Its manual explains the SENC design: "The internal SENC chart is saved for future use. The created files are quite large, but is in a format optimized for quick loading. OpenCPN is trading, creation time and size, for fast rendering when actually using the vector chart", and the "Prepare all ENC charts" button "converts all existing S57/S63 charts to an internal SENC format for fast loading ... can take quite some time, depending on your system" ([OpenCPN Chart Files manual](https://opencpn.org/wiki/dokuwiki/doku.php?id=opencpn:manual_basic:set_options:charts:chart_files), [OpenCPN chart installation](https://opencpn.org/wiki/dokuwiki/doku.php?id=opencpn%3Amanual_advanced%3Acharts%3Achart_install)). `s57chart.cpp` rebuilds the SENC when the format version or the cell edition changes and uses GDAL's OGR geometry export during the build ([s57chart.cpp mirror](https://github.com/manimaul/mapsforge-senc-rendertheme/blob/master/opencpn.org-S57-reference/s57chart.cpp)). The lesson for route A: even a C++ project with a GPU path chose to precompile.
- **TypeScript** `devladpopov/s57-parser` (MIT, 19 stars, pushed 2026-10-12): ISO 8211, DSID/DSPM metadata, chain-node topology, polygons with holes, incremental updates (RUIN, FSPC, VRPC, SGCC), experimental S-101 and S-52-style rendering, tested on NOAA cell US5MA12M ([devladpopov/s57-parser](https://github.com/devladpopov/s57-parser)). The most complete small open reference for a port.
- **Go** `tburke/iso8211` (MIT, 18 stars, last push 2019) and `tburke/ihos57` (2015) ([tburke/iso8211](https://github.com/tburke/iso8211)); `beetlebugorg/chartplotter` (MIT) bakes NOAA S-57 or S-101 into S-101-portrayed PMTiles with a Zig core and points to its successor `lookout-marine` (Zig, Metal/Vulkan/SDL3, pushed 2026-10-31) ([beetlebugorg/chartplotter](https://github.com/beetlebugorg/chartplotter), [beetlebugorg/lookout-marine](https://github.com/beetlebugorg/lookout-marine)).
- **Java** `ChristianDenker/s57reader`, copied from the JOSM seachart plugin (GPL), 2020 ([s57reader](https://github.com/ChristianDenker/s57reader)); **C#** `philliphoff/EncDotNet` (MIT, active 2026) ([EncDotNet](https://github.com/philliphoff/EncDotNet)); **C** `sduclos/S52` libS52 viewer (LGPL-3.0, last push 2018) ([sduclos/S52](https://github.com/sduclos/S52)). **Python**: GDAL's own `osgeo.ogr` is the de facto reader, as in GDAL's test `ogr_s57.py` ([ogr_s57.py](https://github.com/OSGeo/gdal/blob/master/autotest/ogr/ogr_s57.py)); no maintained pure-Python S-57 package was found.
- **ENC to tiles converters.** `ogr2ogr` to GeoJSON then tippecanoe is the common pipeline: `motamman/s57Work` (Python, MIT, pushed 2026-11-22) groups NOAA cells by usage band, renders each band two zooms past its native range and merges with tile-join for Signal K / Freeboard-SK ([s57Work](https://github.com/motamman/s57Work)); `Greenroom-Robotics/enc-mapbox-converter` (ISC, last push 2024-06) uses `OGR_S57_OPTIONS=SPLIT_MULTIPOINT=ON,ADD_SOUNDG_DEPTH=ON` ([enc-mapbox-converter](https://github.com/Greenroom-Robotics/enc-mapbox-converter)); `openwatersio/enc-tiles` (Apache-2.0, pushed 2026-11-22) adds MapLibre styles derived from S-52 ([enc-tiles](https://github.com/openwatersio/enc-tiles)); `ivanoats/chartiles` outputs PMTiles ([chartiles](https://github.com/ivanoats/chartiles)). For raster output, `MarekBak/SMAC-M` converts S-57 to shapefiles and generates MapServer mapfiles with nautical styling (MIT, 2019) ([SMAC-M](https://github.com/MarekBak/SMAC-M)); QGIS opens `.000` files through the same GDAL driver and can export tiles, and NOAA's NCC is the official ENC-to-raster renderer for US data.

### 4.4 Vector rendering in Rust without a GPU API

- **tiny-skia** 0.12.0 (BSD-3-Clause, released 2026-02-02, 76 M downloads, 1,693 stars, pushed 2026-08-20). CPU only, anti-aliased fills and strokes, dashing, clipping, patterns, no text. "We support ARM AArch64 NEON as well and there is no need to pass any additional flags"; neither it nor Skia does runtime CPU detection; "tiny-skia is 20-100% slower than Skia on x86-64 and about 100-300% slower on ARM. Which is still faster than cairo and raqote in many cases" ([linebender/tiny-skia](https://github.com/linebender/tiny-skia), [crates.io tiny-skia](https://crates.io/crates/tiny-skia)). The published ARM run was on an Apple M1, not a Pi ([benches README](https://github.com/linebender/tiny-skia/blob/main/benches/README.md)); in that run a "Source Over" blend took about 604 µs in tiny-skia, 256 µs in Skia and 1,534 µs in cairo, and an anti-aliased hairline 2,410 µs versus 1,141 µs without AA, all per iteration of the benchmark's fixed canvas, whose size the results page does not state ([tiny-skia ARM results](https://linebender.github.io/tiny-skia/arm.html)). No Pi numbers were found anywhere; one project is currently measuring a taffy + cosmic-text + tiny-skia stack at 1080p on Pi hardware over DRM/KMS but has posted no results yet ([Signalare/Chalkboard issue 45](https://github.com/Signalare/Chalkboard/issues/45)).
- **raqote** 0.8.5 (BSD-3-Clause, last release 2024-09-11) ([crates.io raqote](https://crates.io/crates/raqote)); slower than tiny-skia in tiny-skia's own benches and less active.
- **lyon** 1.0.19 (MIT OR Apache-2.0, 2026-03-08): "2D Graphics rendering on the GPU using tessellation"; it produces triangle meshes, so on a CPU path it still needs a rasteriser for the triangles ([crates.io lyon](https://crates.io/crates/lyon)).
- **vello** 0.12.0 (2026-11-11) is "A GPU compute-centric 2D renderer" on wgpu; **femtovg** 0.28.0 (2026-10-27) is OpenGL based ([crates.io vello](https://crates.io/crates/vello), [crates.io femtovg](https://crates.io/crates/femtovg)). On the Pi under KMS/DRM, Mesa's V3D gives conformant OpenGL ES 3.1 and V3DV gives Vulkan on Pi 4 and Pi 5 ([Mesa V3D docs](https://docs.mesa3d.org/drivers/v3d.html)), but V3DV does not implement `VK_KHR_display`: on current Pi OS (Mesa 26.2.2, V3D 7.1.10.2, Vulkan conformance 1.3.8.3) SDL's GPU API fails under KMSDRM with "Vulkan can't find any displays" while `testgles2` works ([SDL issue 16511](https://github.com/libsdl-org/SDL/issues/16511), [SDL_gpu on RPi5 and KMSDRM](https://discourse.libsdl.org/t/sdl-gpu-on-rpi5-and-kmsdrm/58194)). So vello/wgpu on Vulkan is out without a compositor; a GLES 3.1 path (femtovg, or wgpu's GL backend) is the only GPU option on the target, and it would change the project's software-texture pipeline.
- **SDL2_gfx.** All primitives take `Sint16` vertex arrays (`filledPolygonRGBA(renderer, const Sint16 *vx, const Sint16 *vy, int n, ...)`); `filledPolygon` is not anti-aliased, and the anti-aliased variant `aapolygonRGBA` draws only the outline ([SDL2_gfx primitives reference](https://www.ferzkopp.net/Software/SDL2_gfx/Docs/html/_s_d_l2__gfx_primitives_8c.html)). Filled polygons use scanline filling, so polygons with holes (every depth area around an island) must be pre-cut, and there is no pattern fill. For chart-quality area fills on top of the existing i16 clipping discipline this is the weakest option; it is adequate only for hairline outlines and small markers.

### 4.5 The vector-tile route

- MBTiles 1.3: the metadata `format` row may be `pbf`, and "`pbf` as a `format` refers to gzip-compressed vector tile data in Mapbox Vector Tile format"; a `json` row with `vector_layers` describes the layers ([MBTiles 1.3 spec](https://github.com/mapbox/mbtiles-spec/blob/master/1.3/spec.md)). The existing MBTiles reader therefore already knows how to fetch the bytes; only the decode and draw change.
- Producers: GDAL's MVT driver writes tilesets and MBTiles ("Write support requires GDAL to be built with libsqlite3 and GEOS support"; `ogr2ogr -f MVT out source.gpkg -dsco MAXZOOM=10`) ([GDAL MVT driver](https://gdal.org/en/stable/drivers/vector/mvt.html)); tippecanoe is the usual alternative and is what the converters in 4.3 use.
- Rust consumers: `mvt-reader` 2.5.0 (MIT, 2026-09-06, decoder) ([crates.io mvt-reader](https://crates.io/crates/mvt-reader)); `geozero` 0.15.1 (2025-12-11) with the `with-mvt` feature for zero-copy reading into geo-types ([crates.io geozero](https://crates.io/crates/geozero)); `mvt` 0.15.0 (2026-08-01) is an encoder ([crates.io mvt](https://crates.io/crates/mvt)); `pmtiles` 0.28.1 (2026-11-13) if a single-file archive is preferred over SQLite ([crates.io pmtiles](https://crates.io/crates/pmtiles)).
- What the tile route loses: MVT clips geometry to tiles and quantises to a tile grid (4096 units is the usual extent), it carries attributes as key/value pairs so S-57 attribute semantics survive only as far as the converter keeps them, and the S-52 look-up and conditional logic has to be re-expressed as a style over those attributes, which is exactly what openwatersio's MapLibre styles do. Soundings as MultiPoint need `SPLIT_MULTIPOINT=ON,ADD_SOUNDG_DEPTH=ON` at conversion.

## 5. Performance evidence

- **Hardware.** Pi 4 Model B: "Broadcom BCM2711, quad-core Cortex-A72 (Arm v8) 64-bit SoC @ 1.8GHz", 1 to 8 GB LPDDR4, OpenGL ES 3.0 ([Raspberry Pi 4 product brief](https://pip-assets.raspberrypi.com/categories/545-raspberry-pi-4-model-b/documents/RP-008344-DS-7-raspberry-pi-4-product-brief.pdf)). Pi 5: "Broadcom BCM2712 2.4GHz quad-core 64-bit Arm Cortex-A76 CPU ... 512KB per-core L2 caches, and a 2MB shared L3 cache", "VideoCore VII GPU, supporting OpenGL ES 3.1, Vulkan 1.2" at 800 MHz, LPDDR4X-4267, "2 to 3× increase in CPU performance" over Pi 4 ([Raspberry Pi 5 product brief](https://pip-assets.raspberrypi.com/categories/892-raspberry-pi-5/documents/RP-008348-DS-10-raspberry-pi-5-product-brief.pdf)).
- **OpenCPN on a Pi 4** (OpenGL renderer, slow mouse pan, OpenCPN 5.8.4): raster charts "OpenGL frame time ~20ms, opencpn 40% CPU"; S-57 ENC set for US NW "OpenGL frame time ~30ms, opencpn 50% CPU"; S-63 encrypted cell "OpenGL frame time ~700ms, opencpn at 100% CPU" ([OpenCPN issue 3789](https://github.com/OpenCPN/OpenCPN/issues/3789)). Forum reports describe background SENC conversion as the main cause of slowness, single-core saturation on a Pi 4 with 380 NOAA cells, and SD-card versus SSD storage making a large difference; no one has published SENC build seconds per cell ([OpenMarine forum](https://forum.openmarine.net/showthread.php?tid=2432), [Cruisers Forum SENC thread](https://www.cruisersforum.com/forums/f134/senc-file-create-makes-opencpn-almost-unusable-138204.html)). A Pi 5 report shows `--rebuild_chart_db` hanging with S-63 cells while the standalone `OCPNsenc` converter completed 288 of 289 LINZ cells ([OpenCPN issue 5364](https://github.com/OpenCPN/OpenCPN/issues/5364)). Takeaway: a GPU-accelerated C++ ENC renderer achieves about 30 ms per frame on a Pi 4 once the data is precompiled.
- **Parse cost (estimate).** No published GDAL S57 timings were found. A harbour cell is about 1 MB of ISO 8211 with 2,400 feature and 4,700 spatial records (section 1). Byte-level parsing of 1 MB plus topology assembly is in the low tens of milliseconds on a desktop core; scaling by the usual 3 to 5 times for an A72 at 1.8 GHz gives **roughly 100 to 300 ms per harbour cell on a Pi 4, 50 to 150 ms on a Pi 5 (estimate)**. A coastal cell such as US3EC08M (3.75 MB, 25 update files to replay) would be several times that. This is far over the 1 ms rule for the main loop and must be a worker thread or an offline step, which is why OpenCPN precompiles.
- **Rasterisation cost (estimate).** Screen 1280 x 800 = 1,024,000 px. If the M1 "Source Over" figure of about 0.6 ms corresponds to a full canvas fill of about 1 Mpx (the benchmark canvas size is unstated, so this is a guess), tiny-skia fills at roughly 0.6 ns/px on an M1; an A76 at 2.4 GHz with NEON is **perhaps 2.5 to 4 times slower per core (estimate)**, giving about 2 ms per full-screen fill on a Pi 5 and about 4 to 6 ms on a Pi 4. A chart frame paints the equivalent of several screen-fulls of area (depth areas, land, pattern fills, then outlines) plus thousands of anti-aliased line segments and several hundred symbols. Budget **(estimate)**: 3 to 5 screen-fulls of fill (6 to 10 ms on Pi 5) plus 5,000 AA segments and 500 small symbol blits (10 to 30 ms) gives **20 to 40 ms per full redraw on a Pi 5 and 50 to 100 ms on a Pi 4**. That is tolerable for a redraw-on-change plotter that otherwise sleeps, and consistent with OpenCPN's 30 ms with a GPU, but it cannot run inside the 16 ms loop iteration; it would need to render into an off-thread surface that is then uploaded to the streaming texture, the same shape as the existing tile loader.
- **Vector tile decode (estimate).** A gzip-compressed MVT tile of a dense harbour area is typically 50 to 500 KB; gunzip plus protobuf decode of that size is a few milliseconds on an A76. A 1280 x 800 view at 256 px tiles touches up to 30 tiles, so a full view decode is **tens of milliseconds (estimate)**, again worker-thread territory, but tiles cache well and the SQLite fetch is already known to be cheap in this codebase.
- **Raster route.** Zero new runtime cost; pre-rendering NOAA's 7,266 cells to raster MBTiles at zooms 8 to 16 is an offline job measured in hours on a desktop **(estimate)** and the output for one cruising region is hundreds of MB to a few GB **(estimate)**, comparable to the raster charts already in `map/`.

## 6. Legal and safety note

- **Legal to use for leisure, not for carriage.** IHO S-66 (Facts about Electronic Charts and Carriage Requirements, Ed 2.0.0, October 2024): "because an ECS, by definition, is not type-approved as meeting the ECDIS performance standards, the use of ENCs in an ECS does not satisfy the ECDIS carriage requirements of SOLAS"; it defines ECS as "Electronic Chart System (does not meet SOLAS requirements)" and notes that where an ECDIS is used to meet carriage requirements it must "be type-approved", "use up to date electronic navigational charts (ENC)" and have "adequate, independent back-up arrangements" ([IHO S-66 Ed 2.0.0](https://iho.int/uploads/user/pubs/standards/s-66/S-66%20Ed%202.0.0_Final.pdf)). A leisure yacht has no SOLAS chart-carriage obligation, so a homebrew plotter showing ENC data is an ECS and is lawful; NOAA says ENCs "are now also being used on simpler electronic chart systems and chart plotters on many types of ships and by recreational boaters" ([NOAA ENC page](https://www.nauticalcharts.noaa.gov/charts/noaa-enc.html)) and its user agreement permits use and redistribution without restriction ([NOAA ENC user agreement](https://www.charts.noaa.gov/ENCs/ENC_Agreement.shtml)).
- **Fidelity is the safety issue.** S-52 exists because "important features (e.g. own-ship symbol, own-ship safety contour, etc.)" must be "more conspicuous than minor features" and the safety contour must show as "a thick line" with "a sharp change in the colour of the depth areas" ([S-52 Ed 6.1.1](https://iho.int/uploads/user/pubs/standards/s-52/S-52%20Edition%206.1.1%20-%20June%202015.pdf)). A vector display that gets the DEPARE/DEPCNT logic wrong, or a raster pre-render that bakes in a safety contour for the wrong draught, is worse than the current raster chart, which at least shows the official cartographer's blue tint. OpenCPN's manual quotes Bowditch on the complementary danger: zooming a vector chart "beyond what can be supported by the source data" and "a false sense of security" ([OpenCPN Chart Files manual](https://opencpn.org/wiki/dokuwiki/doku.php?id=opencpn:manual_basic:set_options:charts:chart_files)). Any ENC display in this plotter should therefore show the compilation scale (DSPM CSCL) and an overscale warning, and should treat the safety contour and depth-unit settings as part of `state.json` validated at the boundary.
- **Update discipline.** NOAA updates weekly ([NOAA ENC user agreement](https://www.charts.noaa.gov/ENCs/ENC_Agreement.shtml)) and an exchange set carries edition and update numbers in DSID ([S-57 Appendix B.1](https://iho.int/uploads/user/pubs/standards/s-57/20ApB1.pdf)); a plotter that displays ENC-derived data should show the edition and update date of the cell under the cursor so the navigator knows how old it is.

## Fit with the current architecture

This section is about this codebase (HEAD `d475fe0`, 9.8 k lines), not about ENCs in general. Figures for the present renderer come from the repository's own benchmarks (`cargo test --release bench_`): a warm `render_frame` at 1600x800 is about 3.1 ms and a `prefetch_step` 11-16 µs.

### What the frame pipeline is today

```
TileStore (SQLite, LRU)  --(z,x,y) blob-->  TileLoader thread  --decoded RgbaImage-->  prefetch_step drain
                                                                                          |
render_frame: pick source zoom, blit the visible 256 px tiles into one RgbaImage ---------+
      |  (Vec<u8>, Rect) uploaded to ONE streaming RGBA texture (main thread, ~3 ms warm)
      v
Screen::show_map: canvas.copy_ex(texture, rotation, fractional-zoom scale)    <- rotation and 240 ms zoom animation are SDL scaling, not re-rendering
overlay::plan(ChartView, shapes) -> Screen::paint(&[Draw])                    <- route, track, boat, AIS, waypoints via SDL2_gfx, in screen space
night layer, bottom bar, stream capture, top bar, dialog, present
```

Three properties of that pipeline decide how each route fits:

1. **The chart is a raster at an integer zoom, scaled and rotated by SDL.** Anything that produces 256 px RGBA tiles slots in without touching `MBTilesRenderer`, `ChartView`, `overlay`, `Screen`, input or the session. Anything that wants to draw in screen space (symbols that stay upright in course-up, text that does not scale during the zoom animation) has to join the `overlay::plan`/`Screen::paint` path, which today is for a few dozen shapes, not thousands.
2. **Missing tiles are already tolerated.** `render_tiles` leaves the background colour where `TileStore::tile` returns `None`, and the loader fills them in later. A slow tile producer therefore degrades to "grey patches for a moment", which is the behaviour the golden rules ask for. The one exception is the documented fallback that decodes a needed tile on the main thread so frames are never partial; with a producer that costs tens of milliseconds per tile that fallback must go, or it blocks the loop.
3. **`ChartView` is the single pixel<->position seam.** Hit tests, overlays and prefetch all use it. A vector chart adds a new question the app has never asked, "what feature is under this pixel" (a buoy's light characteristic, a depth area's range), and that question needs feature geometry at runtime, which only routes A and B keep.

### Route C: pre-rendered raster MBTiles

Runtime change: none. The `map/` directory is scanned at startup and every `*.mbtiles` becomes a `ChangeChart(i)` menu entry; TMS row order and missing metadata are already handled. An S-57 cell set rendered by an offline tool to z8-z16 PNG tiles behaves exactly like the Navionics-derived tiles already in `map/`.

What the app cannot do with it, and the small changes that would help:

- **No feature pick, no runtime safety contour, no SCAMIN decluttering.** Everything is baked at tiling time. The offline tool chooses the safety contour and the display category; changing them means re-tiling.
- **Night palette.** S-52 defines separate day/dusk/night colour tables; the app's night mode is a dark translucent layer over whatever tiles say. Acceptable for a first pass; a faithful night chart means tiling three MBTiles and teaching `ChartsConfig`/`MenuBar` that one logical chart has palette variants (a small change, one `ChangeChart` per variant is the zero-code fallback).
- **Overzoom.** Beyond the top tiled zoom the raster blurs, as it does for the satellite charts today.
- **Disk.** Same order as the existing z8-18 satellite sets the user already keeps; a harbour-scale ENC rendered to z17 is tens of MB per island group (estimate; depends on the tiler's PNG settings).

Verdict: zero engineering in this repository, all of the effort is in the offline pipeline and in obtaining cells. This is the only route that is independent of the Raspberry Pi's CPU.

### Route B: vector tiles in MBTiles, rasterised on the device

MBTiles 1.3 allows `format = pbf` with gzip-compressed Mapbox Vector Tiles, and `TileStore` already fetches blobs by `(z, x, y)` and caches a decoded `Tile { image, opaque }`. The natural seam is **inside `tile_store`**: a `TileSource` with two adapters, "decode PNG/JPEG" (today) and "decode MVT, apply a style, rasterise 256 px with `tiny-skia`". `MBTilesRenderer::render_tiles` and everything above it would not know the chart was vector; the LRU, prefetch and drain stay as they are. That is a real seam by the codebase-design rule (two adapters that genuinely vary), and it is testable: a fixture MBTiles with one hand-written PBF tile and a style, asserting the colour under a depth area.

Costs and implications:

- **Per-tile cost moves from a PNG decode (~1 ms) to a rasterisation.** Section 5 estimates 50-100 ms for a full 1280x800 redraw on a Pi 4 (20-40 ms on a Pi 5); a 256 px tile is about a sixteenth of that screen, so roughly 3-6 ms per ordinary tile and 10-20 ms for a dense harbour tile on a Pi 4 (estimate). A 1600x800 screen needs roughly 7x4 = 28 tiles plus the prefetch ring, so a cold view is 0.1-0.5 s of loader-thread work (estimate), and the first frame shows background where tiles are pending. Panning along a coast reuses the LRU; the loader keeps up at normal panning speed only if the per-tile figure is at the low end. This needs measuring with a prototype before committing, not estimating.
- **The main-thread decode fallback must be removed for this adapter**, and `prefetch_step(8)`'s budget revisited: eight rasterisations in one loop iteration could be 100+ ms of drain time if the drain itself did any work (it does not today; it only moves finished images, so the budget is fine as long as rasterisation stays on the loader thread).
- **Style engine.** A reduced S-52: per object class and geometry type, a fill colour, line style, symbol, and a display category; conditional symbology for `DEPARE` (safety contour, shallow/deep tints), `SOUNDG` (depth numbers), `LIGHTS` (sector arcs). Text in tiles rotates with the chart in course-up, as raster text already does. This is the bulk of the work and it is pure Rust with no SDL, so it tests well.
- **Two things get better than raster.** True overzoom (re-rasterise the top-zoom tile's geometry at z+1..z+3, crisp lines instead of blur), and a feature pick: the decoded tile's features are in memory, so `ChartView::to_lonlat` plus a point-in-polygon on the tile under the cursor answers "what is this" without a second data path.
- **Tooling dependency.** The offline step is GDAL (`ogr2ogr` reading S-57 with `RETURN_PRIMITIVES` off, `SPLIT_MULTIPOINT` on for soundings) into GeoJSON or GeoPackage, then `tippecanoe` or GDAL's MVT driver into MBTiles, with the S-57 attributes carried as tile properties. Nothing on the Pi needs GDAL.

Verdict: the only route that fits the existing module shape and still gives the navigator something raster cannot. Medium effort (style engine plus one adapter), with one performance unknown that a one-day prototype settles.

### Route A: parse S-57 and draw features at runtime

This is what OpenCPN does, and OpenCPN's SENC cache exists because it is slow: ISO 8211 parsing, assembling spatial primitives into feature geometry and applying updates take long enough that the result is serialised to disk once and reused. In this codebase it would mean:

- A new chart kind beside `MBTilesRenderer`, with a `ChartSource` at the renderer level rather than at the tile level: cell discovery and update application, a SENC-equivalent cache under `default/` or beside the cells, a spatial index (`rstar`), usage-band selection by scale, and a per-frame feature query against the `ChartView` bounds.
- A per-frame rasterisation of thousands of features into the frame image. At 1280x800 on a Pi 4 that is an estimated 50-100 ms per frame, 20-40 ms on a Pi 5 (section 5), before the per-cell parse of 100-300 ms that OpenCPN avoids with its SENC cache, which is far outside the 16 ms loop. The frame would have to be produced asynchronously on a render thread and swapped in when ready, making the chart lag the boat and the pan; the app has no such mechanism today, and `render_frame` being synchronous is what keeps the loop simple. The practical fix is to rasterise into cached tiles on the worker thread, which converges on route B with a parser attached.
- Screen-space symbols and text (upright in course-up, constant size during the zoom animation) are the one genuine advantage over B, and they would have to be a second overlay layer through `plan`/`paint`, which is sized for dozens of shapes, not thousands; `SDL2_gfx` has no anti-aliasing and an `i16` range, so a software rasteriser would still be needed.
- Dependencies: either `libgdal` on the Pi (a large native dependency, the first the app would have beyond SDL2 and SQLite) or a pure-Rust S-57 parser, of which the research found none that assembles features or applies updates (section 4.2: only an ISO 8211 record layer exists).
- Testing: no fixture cell exists and GDAL's S-57 writer is limited, so the TDD seams the repository relies on (`fixture_chart` writes a real MBTiles file) would need a hand-built ISO 8211 cell generator first.

Verdict: a different application. The effort is an order of magnitude above B and the per-frame cost does not fit the render thread on a Pi without re-architecting the loop.

| Item | Today (raster) | Route C | Route B | Route A |

### The decision that comes before any of this

Everything above assumes S-57 cells for the waters sailed can be obtained in the clear. For the Azores, Madeira, the Canaries and the Portuguese and Spanish coasts, the research (section 2) found no free ENC source: those cells are sold through PRIMAR/IC-ENC as S-63 encrypted exchange sets whose permits are bound to an OEM-registered system, which a homebrew plotter cannot be. Free S-57 is, in practice, NOAA (US waters) plus inland European waterways. So for this user the honest ordering is:

1. Settle the data question first: is there any clear S-57 coverage for the intended cruising ground, or is the real need "a better chart than the Navionics screenshots", which OpenSeaMap vector data or commercial raster tiles answer without S-57 at all.
2. If clear cells exist for part of the route (for example a US leg), take route C immediately, no code, and judge the result on the water.
3. If a feature pick or runtime safety contour turns out to matter, prototype route B's rasteriser on the Pi for a day and measure the per-tile cost before designing the style engine.
4. Rule route A out of scope for this codebase unless the Pi gains a GPU path the app is willing to depend on.
